# Storybound（入戏）- 开源产品学习

本文记录与 Storybound 相邻的开源产品、可复用的产品经验和需要保持的设计边界，作为后续产品完善与功能评审的参考。

调研快照日期：2026-08-15。Storybound 本地实现状态更新日期：2026-08-17。项目功能会持续变化，实施前仍应重新核对上游文档和许可证。本文只比较公开功能与产品方向，不代表对上游项目质量的完整评价。

## 一、结论

GitHub 上存在多款 AI 角色扮演、AI 续写和互动叙事项目，但目前没有发现与 Storybound 完全相同的开源产品。最接近的产品是 SillyTavern、RisuAI 和 Agnai；KoboldAI Client 更接近 AI 续写与文字冒险；Ink 和 Twine 不包含 AI，但适合学习确定性的故事节点与条件系统。

现有产品普遍擅长：

- 角色卡、玩家 Persona 和角色聊天。
- Lorebook、World Info、提示词预设和长期记忆。
- 多模型 Provider、消息重生成、候选回复和聊天分支。
- 插件、脚本、主题和多媒体扩展。

Storybound 应继续坚持的差异是：

- 故事卡表示一个可重复游玩的完整故事，而不只是一个聊天角色。
- 每次对话都是独立存档，创建后使用不可变的故事与玩家配置快照。
- 消息路径、能力消耗、故事状态、节点进度、知识簿和 MOD 配置共同绑定运行时检查点。
- 故事进行中的 MOD 或状态变化形成可见事件，只影响之后的生成。
- 事实、人物知情范围和用于召回的记忆相互分离。
- 模型只能提出结构化变化建议，不能直接修改受保护状态。

因此，学习目标不是把 Storybound 变成另一款角色聊天前端，而是吸收成熟项目的交互与生态兼容能力，同时保留可靠的故事状态模型。

## 二、项目对比

### 1. SillyTavern

- 仓库：[SillyTavern/SillyTavern](https://github.com/SillyTavern/SillyTavern)
- 定位：面向高级用户的通用 LLM 角色扮演前端。
- 许可证：AGPL-3.0。

主要重叠：

- 角色卡、玩家 Persona、群聊和多模型 Provider。
- World Info、提示词预设、上下文管理和扩展系统。
- 同一轮候选回复、消息编辑、重生成和聊天管理。
- 本地运行、数据导入导出和大量社区格式。

值得学习：

- 角色卡和 World Info 生态兼容，降低内容迁移成本。
- 候选回复切换的轻量交互，以及当前候选的明确标识。
- 提示词分区、上下文检查和 Token 预算的可见性。
- Provider 能力差异的统一设置体验。
- 高级功能按面板分区，避免阻塞基本聊天流程。

不应照搬：

- 以角色为中心的数据模型。Storybound 的一级对象仍应是故事卡。
- 只切换显示文本的候选回复语义。Storybound 必须同步切换运行时检查点。
- 任意第三方扩展直接进入服务进程。Storybound 的可信代码 MOD 与声明式用户 MOD 必须分开。
- 为高级用户不断叠加入口而造成的界面密度。常用游玩流程应保持稳定、克制。

### 2. RisuAI

- 仓库：[kwaroran/RisuAI](https://github.com/kwaroran/RisuAI)
- 定位：跨平台 AI 角色聊天客户端。
- 许可证：GPL-3.0。

主要重叠：

- 角色卡、群聊、Lorebook、分支和多模型 Provider。
- 可调整顺序、条件和变量的提示词系统。
- 插件、正则脚本、聊天资源和移动端体验。
- HypaMemory、SupaMemory 等长对话记忆方案。
- 对话级 Lorebook 与角色级 Lorebook 的作用域划分。

值得学习：

- 提示词顺序、条件、变量和启用状态的可视化配置。
- 全局内容与当前对话内容之间清晰的作用域提示。
- 分支操作在聊天时间线中的呈现方式。
- 长期记忆对最近内容、摘要内容和相关召回内容的预算划分。
- 跨平台和窄屏下的聊天、侧栏与设置交互。

不应照搬：

- 用提示词变量代替应用事实状态。提示词可以描述状态，但不能成为状态真相来源。
- 用正则脚本直接修改模型输出后隐式改变剧情结果。
- 把未知插件视为普通内容导入。插件必须有权限、来源和执行边界。
- 让记忆摘要覆盖已确认事实；记忆只能辅助上下文召回。

### 3. Agnai

- 仓库：[agnaistic/agnai](https://github.com/agnaistic/agnai)
- 定位：支持自托管的 AI 角色扮演与人物聊天平台。
- 许可证：AGPL-3.0。

主要重叠：

- 多种 Persona 格式、群聊和多模型服务。
- Memory/Lorebook、生成预设和可选长期记忆能力。
- 自托管与浏览器本地数据模式。

值得学习：

- 不同 Persona 格式的归一化导入流程。
- Provider、生成预设和角色内容之间的配置边界。
- 无完整服务端依赖时仍可使用的降级运行方式。

不应照搬：

- 账号、多租户、订阅和多人聊天能力。这些不属于当前单人本地产品范围。
- 把人物聊天作为全部信息架构的中心。
- 为部署形态引入 Storybound 当前不需要的数据库与基础设施复杂度。

### 4. KoboldAI Client

- 仓库：[KoboldAI/KoboldAI-Client](https://github.com/KoboldAI/KoboldAI-Client)
- 定位：支持本地与远程模型的 AI 辅助写作和文字冒险前端。
- 许可证：AGPL-3.0。

主要重叠：

- Novel、Adventure 和 Chatbot 等不同创作模式。
- Memory、Author's Note、World Info、保存与加载。
- 本地模型与远程模型服务。

值得学习：

- 对话、行动和旁白模式应给模型不同而明确的输入语义。
- 作者说明与故事正文分离，适合作为导演指令交互的参考。
- 自由续写场景下快速编辑、继续和回退的操作效率。
- 保存文件的可移植性与离线使用预期。

不应照搬：

- 以一段持续增长的自由文本作为全部故事状态。
- 把模型加载和推理运行时直接并入 Storybound。模型服务应继续通过适配器连接。
- 让模式差异只依赖提示词约定；确定性状态变化仍应由应用处理。

### 5. KoboldCpp

- 仓库：[LostRuins/koboldcpp](https://github.com/LostRuins/koboldcpp)
- 定位：本地 GGUF 模型推理运行时，附带 API 和轻量界面。

它不是 Storybound 的直接竞品，更适合作为本地模型 Provider 参考。Storybound 可以验证与其 OpenAI-compatible 或 Kobold API 的连接体验，但不应承担模型下载、显存分配、量化和推理优化等职责。

值得学习：

- 本地服务发现、连接测试和能力探测。
- 上下文长度、停止词、流式输出等兼容性提示。
- 本地 Provider 离线、重启和端口变化时的错误反馈。

### 6. Ink 与 Twine

- 仓库：[inkle/ink](https://github.com/inkle/ink)
- 编辑器：[inkle/inky](https://github.com/inkle/inky)
- 仓库：[klembot/twinejs](https://github.com/klembot/twinejs)
- 定位：确定性的分支互动叙事语言与编辑工具，不负责 AI 生成。

主要重叠：

- 故事节点、条件、变量、选择、跳转和完成状态。
- 可测试的确定性故事流程。
- 内容与运行时之间相对清晰的边界。

值得学习：

- 节点条件应使用受限 DSL 或结构化表达式，不能执行任意代码。
- 编辑期校验不可达节点、循环、缺失目标和变量类型错误。
- 运行时保存节点位置与变量状态，而不是从故事文本反推进度。
- 作者可以表达结构，但玩家界面不必暴露完整流程图。

不应照搬：

- 把所有剧情预先写成确定性分支。Storybound 的节点应约束和引导 AI，而不是替代生成。
- 第一阶段就建设大型可视化节点编辑器。先验证节点模型与运行时语义，再决定编辑形式。

## 三、能力对照

下表用于快速选择参考对象。“部分”表示存在相邻功能，但其数据语义与 Storybound 不完全相同。

| 能力 | SillyTavern | RisuAI | Agnai | KoboldAI | Ink/Twine | Storybound 目标 |
|------|-------------|--------|-------|----------|-----------|-----------------|
| 角色/玩家设定 | 强 | 强 | 强 | 部分 | 无 | 故事内多人物与玩家快照 |
| 完整故事模板 | 部分 | 部分 | 弱 | 部分 | 强 | 故事卡作为一级对象 |
| 同模板多存档 | 强 | 强 | 强 | 强 | 强 | 独立且不可变的设定快照 |
| 回复候选与分支 | 强 | 强 | 部分 | 部分 | 强 | 消息与运行时检查点同步切换 |
| 世界信息与记忆 | 强 | 强 | 强 | 强 | 部分 | 事实、知情范围、摘要和召回分离 |
| 结构化故事状态 | 弱 | 部分 | 弱 | 弱 | 强 | Schema 校验、事件历史和撤销 |
| 故事节点与条件 | 弱 | 部分 | 弱 | 弱 | 强 | 节点引导 AI，确定性条件由应用执行 |
| 扩展或插件 | 强 | 强 | 部分 | 脚本 | 部分 | 可信 MOD 与声明式 MOD 分层 |
| 进行中扩展变更 | 有 | 有 | 部分 | 有 | 不适用 | MOD 快照、检查点和时间线事件 |
| 本地模型接入 | 强 | 强 | 强 | 强 | 不适用 | OpenAI-compatible Provider 优先 |

## 四、Storybound 当前落地状态

本节按当前代码实现整理，状态快照日期为 2026-08-17。这里的“已落地”表示已有可运行功能和测试覆盖，不表示最终产品体验已经完成；项目尚未正式开始使用真实数据，当前状态仅作为开发期标记。

### 已落地

1. 故事卡作为一级对象已经成立。当前支持故事库、故事详情、内置故事、故事草稿、编辑、复制、发布、删除草稿和故事卡体检；编辑时会保留仍存在的人物、能力、场景和玩家模板 ID。
2. 同故事多存档与不可变快照已经成立。创建对话时保存故事卡、玩家、能力、开场、模型 Provider 和 MOD 配置快照；之后修改故事卡不会静默影响旧存档。
3. 消息路径和运行时检查点已经绑定。消息树、`active_leaf_message_id`、`active_checkpoint_id`、状态快照、能力快照和 MOD 快照共同决定当前采用路径。
4. 最后一轮候选回复和分支语义已经有基础实现。重新生成会创建兄弟回复，候选列表可以切换当前采用版本，切换时同步更新消息叶和运行时检查点；服务端也能返回分支树、派生来源和候选并排比较所需数据。
5. 玩家输入模式已经区分为对话、行动和旁白，并写入消息存储和提示词历史，不再只依赖自然语言约定。
6. 流式生成、停止、失败重试、重新生成和编辑后重试已经形成闭环。模型失败时保留玩家消息，完成时再事务性写入模型回复和新检查点。
7. 上下文预览已经可解释。系统会展示应用规则、故事背景、玩家快照、场景、人物、能力、记忆、MOD 和历史消息的预算、来源、作用域、裁剪原因，并在生成完成后记录真实 input token 与估算误差。
8. 本地数据闭环已经具备。支持 SQLite 存储、私有文件权限、备份列表、创建备份、下载备份、恢复备份、恢复前安全备份和 Markdown 导出。
9. OpenAI-compatible Provider 管理已经具备。支持本地/远程 Provider、默认 Provider、凭据版本快照、健康检查、连接错误归一化、流式协议严格校验、超时和 429 遥测。
10. 可信 MOD 运行时已经具备基础能力。设置页可管理内置可信 MOD；对话中可启停和配置 MOD；变更会创建检查点和时间线事件；生成期间禁止修改；当前内置 MOD 包括叙事视角、叙事风格、连续性守卫和节奏导演。节奏导演会读取当前检查点中的 pending 状态建议、进行中节点和消息深度，动态调整本轮推进建议。
11. 章节与记忆已有最小闭环。用户可以固定当前路径消息为记忆，可以结束章节并保存摘要；固定记忆和章节回顾会进入后续提示词预算。
12. 固定结构校验已由 Zod 统一到共享契约。API 请求、响应 DTO、SSE 事件、故事草稿、对话输入和 MOD 配置都有前后端共享校验。
13. 动态自定义状态的第一版 Ajv 校验已接入。故事卡可以保存受限 JSON Schema、默认自定义状态和字段策略；保存故事草稿、写入场景初始状态和创建对话时会校验 `state.custom` 中故事作者定义的字段。应用自有的 `pinnedMemories`、`chapterSummaries`、`abilityUses`、`stateSuggestions` 和 `nodeProgress` 仍由固定 Zod 结构管理。
14. 访问控制和本地安全基线已经具备。非回环监听必须配置访问令牌；远程模型 Provider 必须使用 HTTPS 公网地址，并拒绝解析到私网、回环或链路本地地址。
15. 自动化测试基础已经覆盖主要边界，包括共享 Schema、生成协议、候选回复、检查点、MOD、备份恢复、访问控制、索引计划、前端 API/SSE 和核心 Playwright 流程。
16. 故事编辑器已有“状态结构”基础面板。作者可以用表单维护常见自定义状态字段、默认值、必填项和玩家可编辑策略；高级 Schema、节点条件和 MOD 配置仍可通过带校验的 JSON 字段编辑。
17. 从历史消息派生独立对话已经落地。系统会复制当前采用路径到目标消息、相关章节、消息、运行时检查点、MOD 快照和状态快照，并在源存档与新存档写入派生事件。
18. 时间线事件类型已经扩展到章节结束、固定/取消记忆、状态更新、能力使用、状态建议创建/接受/拒绝、节点进度更新和存档派生；对话页会统一呈现这些事件。
19. 上下文检查器已经展示估算偏差。生成完成后保存真实 input token、估算误差、误差率和测量时间，检查器会显示校准结果。
20. Storybound 自有故事卡 JSON 包导出已经落地。导出包包含格式名、格式版本、导出时间、兼容信息、故事设定、人物、能力、开场、动态状态 Schema、事实、世界书条目、节点和声明式 MOD。
21. 能力运行时已有第一版。能力可以保存配置 Schema、输入 Schema、结果 Schema、单存档使用次数、冷却轮数和确定性 `statePatch`；执行时会校验输入、检查次数/冷却、写入新检查点和能力使用事件。
22. 状态变化建议确认流程已有第一版。系统支持创建 pending 状态建议，并由用户接受或拒绝；只有接受后才会把结构化 patch 写入故事状态。状态编辑、能力执行、建议创建和建议接受都会记录字段级 diff，并进入事件历史；服务端已提供状态建议列表和状态字段保护说明。
23. 事实、秘密和人物知情范围已有结构化模型。故事卡可以保存公开事实和秘密事实；提示词只注入公开事实以及当前在场人物知情的秘密，并标注不能无故向玩家揭露。
24. 故事节点与受限条件系统已有基础运行时。节点支持启用状态、结构化条件、说明和提示词；运行时会按 `phase`、`location`、`time` 和 `custom` 条件筛选命中节点，结合 `nodeProgress` 过滤已完成或已跳过节点，并作为动态机会池注入上下文预算；服务端已支持节点状态机、可达性诊断、激活、取消激活、完成和跳过。
25. 声明式 MOD 清单已有基础格式。故事卡可以保存声明式 MOD 的名称、版本、说明、配置 Schema、默认配置、默认启用状态和提示词贡献；默认启用的声明式 MOD 会进入提示词预算。
26. 服务端 Prompt Compiler 已有第一版。核心规则、故事背景、玩家快照、当前场景、动态故事状态、人物、事实、世界书召回、节点机会池、能力、记忆、声明式 MOD、可信 MOD、历史消息和本次输入会归一成 `PromptBlock`，记录来源、作用域、优先级、预算、hash、依赖和裁剪原因，并把 `promptSnapshot` 写入上下文估算；Prompt profile 的 block 顺序、预算比例和显示标签已集中在服务端 registry，并可通过只读接口查看。
27. 动态故事状态已进入服务端提示词编译。作者自定义状态字段会按字段策略和 Schema 标题渲染为可读状态；pending 状态建议、能力使用次数和节点进度也会进入独立 `state.story-dynamics` block。
28. 故事卡内自有 Lorebook 已有基础闭环。作者可以保存标题、内容、关键词、结构化条件、优先级、启用状态和故事/场景/人物/章节作用域；创建对话时会进入故事快照，生成前按本轮输入、当前场景和在场人物做关键词与条件召回，并以独立 `story.lorebook.matched` block 注入预算。服务端已提供召回诊断，能解释 disabled、scope、condition 和 keyword 未命中原因。它是背景资料召回，不等同于已确认事实。
29. Storybound 自有故事卡 JSON 导入已有基础。导入接口支持 dry-run 报告、格式版本校验、未知顶层字段报告、媒体引用清单、体检问题汇总和创建导入草稿；导入内部已拆成 normalize、format detect 和 adapter pipeline，故事库已有 JSON 导入面板，可以检查报告并进入导入草稿。
30. SillyTavern V2 角色卡已有有损导入适配。系统能把角色卡转换为单人物 Storybound 故事草稿，把问候语映射为默认开场，把 `character_book` 条目映射为故事 Lorebook，并在导入报告中标明转换损耗；该能力已作为导入 adapter 接入统一管线。
31. 对话页已有故事诊断抽屉。它能展示状态建议 diff、状态字段保护说明、节点诊断与手动进度操作、Lorebook 召回诊断、召回质量、分支树和候选回复比较。
32. 召回质量诊断已有服务端基础。系统会把 Lorebook、固定记忆和章节回顾统一列为候选资料，按当前输入给出轻量相关性评分，并明确区分背景资料、已确认记忆和章节摘要；服务端已抽象 RecallSource registry，并暴露 lexical engine 与 FTS5-ready source 能力标记。
33. Prompt profile 审计已有基础。服务端可返回 profile hash、顺序/必需块/召回顺序检查和 prompt golden scenario 定义；真实 prompt snapshot 已接入 golden 评估测试，设置页会显示审计结果，供后续模型评测和回归测试使用。
34. 状态变更统一提交管线已落地。状态编辑、能力执行、状态建议创建/接受和节点进度更新现在共用 StateMutation 管线，统一执行活动叶与检查点并发校验、状态校验、检查点克隆、事件写入和返回结构。

### 部分落地

1. 故事状态已有编辑、字段策略校验、建议确认闭环、统一 StateMutation 提交管线、服务端字段级 diff、状态建议列表、字段保护说明、诊断面板展示和动态状态提示词 block；应用管理字段会被服务端拒绝直接修改。但更友好的非 JSON 编辑体验和状态撤销 UI 仍需继续打磨。
2. 能力运行时已有确定性状态提交、输入校验、次数、冷却、使用计数和时间线事件；事件 payload 会记录输入和状态 patch。但还没有独立结果对象、消耗模型、能力执行日志详情、配置 UI 和外部工具调用。
3. 长期记忆已有固定记忆、章节摘要、故事卡内世界书关键词召回、作用域、召回诊断、RecallSource 抽象和轻量召回质量评分；但还没有独立外部 Lorebook/World Info 导入、实际 FTS5 索引、跨故事知识簿作用域和长期质量评估。
4. MOD 已经有可信代码插件、按存档配置快照和声明式 MOD 基础格式；但声明式 MOD 仍是故事卡内的提示词贡献，没有外部 MOD 导入、权限清单、版本兼容策略和安全安装流程。
5. 分支能力已覆盖最后一轮候选切换、历史消息派生、派生存档命名、来源/子存档事件记录、分支树数据、候选比较数据和诊断面板浏览；但还没有来源跳转、历史保护 UI 和更适合长分支树的导航。
6. 故事编辑器已经支持基础设定、人物、玩家模板、能力、状态结构、事实、世界书、节点、声明式 MOD 和开场；但复杂 Schema、世界书附加条件与复杂节点条件仍主要依赖 JSON 字段。
7. 上下文检查器已经能显示最终提示词、预算和估算校准；Prompt audit 已有基础 golden scenario 定义，真实 prompt snapshot 已有确定性 golden 测试。但还没有模型间效果评测、失败案例标注和提示词预设导入导出。
8. 时间线事件已有多类运行时事件，节点机会池也会跳过已完成或已跳过节点，节点进度变更已有服务端状态机、事件和诊断面板操作；但场景切换、阶段变化、节点自动命中和节点完成建议还没有完整打磨。
9. Storybound 自有故事卡 JSON 包已有导出、导入 dry-run/创建草稿和导入报告 UI；SillyTavern V2 角色卡已有单人物草稿转换，并已接入统一 import adapter pipeline。但还没有媒体文件实际打包/复制、跨版本兼容矩阵和更多外部格式适配。

### 尚未落地

1. 常见角色卡导入：SillyTavern V2 已有基础转换；RisuAI、Agnai、多人物卡和更完整映射预览仍未落地。
2. 外部 Lorebook/World Info 导入：SillyTavern 角色卡内 `character_book` 可随角色卡导入；独立世界书导入、触发条件转换和作用域确认仍未落地。
3. 玩家档案库：当前新建对话只填写本次玩家信息，还没有可复用的全局玩家档案管理。
4. 导演指令面板：当前有节奏/风格类 MOD、声明式 MOD、动态节奏导演和行动快捷输入，但没有单次、本章节、本对话作用域的独立导演指令记录。
5. 资源库：尚未建设世界书、人物原型、故事节点模板、MOD 模板等可复用资源库。
6. 内容生态兼容：尚未支持提示词预设导入导出、外部主题/资源包、媒体资源打包和许可证扫描。

### 后期兼容：吸收成熟内容生态

1. 扩展常见角色卡导入，把 RisuAI、Agnai、多人物卡和更复杂变量映射为故事卡人物或故事草稿；导入前必须展示映射结果。
2. 支持独立 Lorebook/World Info 的受限导入，将条目映射为背景资料或知识簿草稿，不直接认定为已确认事实。
3. 支持提示词预设的导入导出，但 Provider 凭据、服务端路径和可信代码 MOD 不得进入预设。
4. 对导入内容运行确定性体检，报告缺失人物、冲突规则、未知变量和不支持的扩展字段。
5. 在确有内容规模需求后再建设世界书、人物原型和 MOD 的可复用资源库；资源进入存档时仍需生成快照。

## 六、明确不做的方向

- 不在当前阶段建设账号、云同步、社区市场、评论评分、订阅和多人实时协作。
- 不把 Storybound 变成通用模型运行器或模型下载工具。
- 不允许浏览器上传任意服务端代码并当作安全插件执行。
- 不用正则处理或模型自然语言替代结构化状态事务。
- 不让故事卡编辑覆盖已经开始的对话。
- 不为了兼容外部格式而丢失 Storybound 的故事卡、检查点和知识边界语义。
- 不直接复制 AGPL/GPL 项目的源码或界面实现；引用实现前必须单独进行许可证评估。

## 七、功能设计时的参考清单

后续设计功能前，先选择最相关的参考项目：

| Storybound 功能 | 首选参考 | 重点观察 |
|-----------------|----------|----------|
| 角色卡导入 | SillyTavern、RisuAI、Agnai | 格式识别、字段映射、未知字段和导入预览 |
| Lorebook/知识簿 | SillyTavern、RisuAI | 触发条件、作用域、预算，以及提示信息与事实的区别 |
| 回复候选与分支 | SillyTavern、RisuAI | 当前候选标识、历史保护、派生入口 |
| 长期记忆 | RisuAI、Agnai | 最近消息、阶段摘要、相关召回和预算分配 |
| 导演指令 | KoboldAI Client | Author's Note 与正文分离、作用范围和持续时间 |
| 故事节点 | Ink、Twine | 条件表达、变量、可达性检查和运行时保存 |
| Provider 设置 | SillyTavern、RisuAI、KoboldCpp | 能力探测、连接测试、错误归一化和本地离线状态 |
| MOD 系统 | SillyTavern、RisuAI | 安装体验、配置作用域和安全提示；执行边界使用 Storybound 自有设计 |

每次评审至少回答以下问题：

1. 这个功能解决的是故事创作、游玩控制还是系统管理问题？
2. 哪些数据是模板，哪些是存档快照，哪些只是当前页面状态？
3. 功能改变消息路径时，关联的结构化状态如何切换？
4. 内容属于已确认事实、人物认知、记忆摘要还是临时提示词？
5. 修改何时生效，是否需要检查点、时间线事件或用户确认？
6. 模型离线、生成失败、服务重启和数据导入失败时是否仍可恢复？
7. 是否能用声明式数据完成，还是确实需要受信任代码扩展？
8. 引入外部格式或代码前，许可证、安全和版本兼容边界是否明确？

这份文档用于提供参考而不是自动扩张范围。新增能力仍应服从 `PRODUCT.md` 的阶段目标和 `TECH.md` 的数据一致性约束。
