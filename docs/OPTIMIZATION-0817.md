> 复核基线：2026-08-17 当前工作区。该目录未包含 Git 元数据，正式归档时应补充 commit SHA。

## 一、阅读规则

### 1.1 证据等级

| 等级 | 含义 | 写作要求 |
|------|------|----------|
| 已核实 | 可由当前源码、测试或可重复操作直接确认 | 标注文件与关键 symbol，避免只引用易失效的行号 |
| 待测量 | 从实现可以推断风险，但缺少性能数据或故障样本 | 先定义基线和成功阈值，再决定是否实施 |
| 产品假设 | 可能改善体验，但尚无用户研究或行为数据支持 | 先做原型或可用性测试，不直接承诺开发 |

### 1.2 优先级

| 优先级 | 定义 |
|--------|------|
| P0 | 已复现的数据丢失、安全问题或核心流程完全不可用，需要立即处理 |
| P1 | 直接影响核心游玩流程可靠性、可恢复性或可诊断性，应在当前阶段处理 |
| P2 | 有明确收益，但可以在基线测量、依赖能力或产品验证完成后实施 |
| P3 | 面向未来范围、局部打磨或尚未满足触发条件的工作 |

当前没有经过验证、满足上述定义的 P0。若线上或验收中出现可复现事故，应按证据重新调整，而不是因为“看起来重要”直接升为 P0。

工作量使用相对估算：S 为局部、低耦合改动；M 为跨模块改动；L 为包含数据迁移、基础设施或持续评测的改动。估算只用于排序，不代替实施拆解。

## 二、总体结论

当前项目已经具备较好的工程基础：

- Prompt 按块分配预算，并有组装期硬校验。
- `promptHash`、`finalSystemHash` 和 block 明细随生成保存，可用于审计和回归。
- Provider endpoint 校验配合 `redirect: 'error'` 防护 SSRF，访问令牌使用 `timingSafeEqual` 比较。
- `expectedLeafMessageId` 和 `expectedCheckpointId` 贯穿关键写操作，具备乐观锁基础。
- 前后端共享 Zod 契约，SSE 事件使用判别联合校验；前端已经有 rAF 批处理和恢复查询。
- 服务启动时已经处理遗留的活跃生成；仓库已经存在基础 Playwright E2E 用例。

当前阶段建议先完成五件事：

1. 为上下文预算建立按模型校准的测量闭环和确定性降级策略。
2. 为渲染异常、生成竞态和服务重启补齐可恢复性测试。
3. 建立不记录 Prompt 正文和凭据的结构化日志，给后续性能优化提供基线。
4. 用固定语料评估召回质量，再决定 FTS、混合检索或向量检索的实施范围。
5. 为模型评测和故事卡 AI 审阅加入 LLM Judge 偏差控制，确定性约束继续由代码测试判定。

## 三、AI 与 Prompt

### 3.1 上下文 Token 预算闭环

**证据等级**：已核实  
**优先级 / 工作量**：P1 / M

**现状**

`apps/server/src/services/prompt/contextCache.ts` 的 `estimateTokens` 使用 `CJK × 1.15 + other / 3` 估算；`withActualInputTokens` 会记录实际输入 token 和误差，但目前不会影响下一轮预算。`apps/server/src/services/prompt/assembly.ts` 使用固定比例的 `envelopeReserved`。

**风险**

不同 Provider、模型和消息封装格式的误差并不一致。估算偏小时，Provider 可能返回 `MODEL_CONTEXT_LIMIT`；估算偏大时，则会过早丢弃可用上下文。一次实际 usage 不能直接代表后续请求，也不应让预算在少量样本下频繁波动。

**建议方案**

1. 对提供官方 tokenizer 的模型使用对应 tokenizer；无官方 tokenizer 时保留启发式估算，并按 `provider + model + 消息格式版本` 分组校准。
2. 只记录 token 数和误差，不记录 Prompt 正文。使用滚动窗口的保守分位数调整安全余量，并设置上下限，避免单次异常改变预算。
3. 上下文超限时最多自动重试一次。重试按确定顺序移除最旧且未固定的历史、低优先级召回结果和可重新生成的旧摘要。
4. 应用规则、世界硬规则、当前输入、已确认事实和用户固定记忆不得静默删除。若仍然超限，返回可操作提示，而不是继续重试。
5. 在生成记录中保存首次估算、裁剪项、重试原因和最终 usage，便于审计额外调用成本。

**验收标准**

- 建立覆盖中文、英文、混合文本和长历史的固定 token 语料集。
- 对支持官方 tokenizer 的模型，测试语料的 token 计数与实际请求格式一致。
- 对无法精确分词的模型，测试集中的低估误差能够被安全余量覆盖；阈值在采样后固化，不在实现前拍定。
- 模拟 `MODEL_CONTEXT_LIMIT` 时最多重试一次，不重复保存玩家消息，不改变必需 Prompt 块，并能从生成记录看出裁剪原因。
- 页面明确区分“发送前估算”和“Provider 返回的实际 usage”。

**依赖与风险**

需要先建立模型标识和消息格式版本的稳定键。自动重试可能产生额外费用，因此必须有次数上限、审计记录和用户可见状态。

### 3.2 召回性能与召回质量分开治理

**证据等级**：实现已核实，收益待测量  
**优先级 / 工作量**：评测 P1 / S，实施 P2 / M-L

**现状**

`apps/server/src/services/conversationManagement/recallSources.ts` 中的召回引擎是基于中文 2/3-gram 的 lexical 匹配。`fts5Ready: true` 是能力元数据字段，但当前执行路径没有使用 FTS5，文档不应把该字段当成已经接入索引的证据。lorebook 仍会遍历当前故事卡中的条目并执行确定性条件和关键词判断。

Lexical 本身属于检索方式，不应称为“占位”或“不是真正检索”。当前需要区分两个问题：全量遍历是否造成性能瓶颈，以及 lexical 是否造成相关记忆召回质量不足。

**建议方案**

1. 先建立固定召回语料：包含当前输入、应命中项、不应命中项、权限范围和命中原因。
2. 对 100、1,000、10,000 条数据分别测量召回延迟和组装总耗时。只有全量遍历形成可见瓶颈时，才实施索引化。
3. 若使用 SQLite FTS5，需要明确中文分词策略；默认 tokenizer 不应未经对比直接替换当前 n-gram。
4. lorebook 保留关键词、作用域和条件匹配的确定性语义。语义检索可以补充候选，但不能绕过 `enabled`、scope、condition 和知识权限过滤。
5. pinned memory 和 chapter summary 可以比较 lexical、FTS、hybrid、vector 四种方案。向量方案必须同时评估嵌入模型体积、首次建索引耗时、增量更新、重建和离线可用性。

**验收标准**

- 固定数据集报告 Recall@K、误召回率和权限泄漏数；权限泄漏必须为 0。
- 新方案相对当前 lexical 基线有明确质量提升，并且没有不可接受的延迟、磁盘或启动成本。
- 索引可从主数据完整重建，新增、编辑、删除和恢复快照后不会产生陈旧结果。
- 召回诊断能够说明命中来源、规则和分数，且不向玩家暴露无权查看的秘密内容。

**决策门槛**

评测完成前只排期语料和基准建设，不预先承诺 FTS5 或向量数据库。

#### SQLite FTS5 的当前判断

**证据等级**：运行时已核实  
**优先级 / 工作量**：对话搜索 P2 / M，Prompt 召回 P2 / M

当前开发环境的 Bun SQLite 为 3.51.0，`sqlite_compileoption_used('ENABLE_FTS5') = 1`，可以直接创建 FTS5 虚拟表。但默认 `unicode61` tokenizer 无法从连续中文“槐安站末班车”中命中“末班车”；内置 `trigram` 可以命中三个及以上字符的“末班车”“旧车票”，不能命中两个字符的“槐安”“车票”。因此“运行时支持 FTS5”不等于“中文召回已经可用”。

FTS5 在当前项目中的适用顺序是：

1. 优先用于对话历史全文搜索，提供 BM25 排序、命中片段、关键词高亮和跳转消息。搜索结果必须限制在目标 conversation；当前版本搜索还要通过活动叶的祖先路径过滤，不能混入其他候选分支。
2. 在召回基准证明有效后，用于从被最近历史预算裁掉的旧消息和章节摘要中选择候选。`pinned` 记忆仍然优先，不能因为没有 FTS 命中而静默删除。
3. lorebook 只有在条目规模和延迟形成实际瓶颈时才使用 FTS 预筛选。FTS 分数不能绕过 `enabled`、scope、condition、章节、人物和知识权限规则。
4. 故事库全文搜索只在卡片数量明显增长后实施；当前前端字符串匹配足够，不作为接入 FTS5 的理由。

中文检索采用两层策略：三个及以上字符可使用 `trigram`；不足三个字符回退到有长度和作用域限制的 `LIKE` 或现有安全 2/3-gram 词项路径。不得回退到会静默漏掉中文结果的 `unicode61`。MATCH 查询只能由白名单化词项构造，并继续使用参数绑定。

FTS 表始终是可重建派生索引，不是消息、记忆、知识簿或故事事实的真实数据源。索引结果进入 Prompt 前还要执行 conversation、活动分支、检查点、权限、去重和 token 预算过滤。表结构、同步与降级规则以 `docs/TECH.md` 的 `memory_fts` 和“记忆检索”章节为唯一长期设计出处。

**验收标准**

- 中文三字词、两字人名/地名、英文单词和混合文本都有固定查询样例。
- 当前分支搜索不会返回其他候选版本的消息，权限泄漏数为 0。
- 索引删除后可以从 SQLite 权威数据完整重建，结果与增量同步一致。
- FTS 不可用或短查询回退时有明确检索模式，不把空结果误报为“没有相关记忆”。
- Prompt 召回上线前，必须证明其相对当前 lexical 基线改善召回质量，而不只是查询更快。

### 3.3 外部 AI 与上下文技术选型

**证据等级**：公开文档与论文已核实，项目收益待评测  
**优先级 / 工作量**：方法借鉴 P1 / S，外部依赖 P3 / L

| 候选 | 可借鉴内容 | 当前决定 |
|------|------------|----------|
| OpenViking | 分层上下文、召回轨迹、会话记忆生命周期 | 不作为当前必选依赖；未来只允许作为可选派生索引，不接管 SQLite、检查点、事实或知识权限 |
| LightRAG | 低层实体与高层主题双通道召回、增量更新、删除重建和来源追踪 | 借鉴召回结构；大型外部世界资料成为真实需求后再做适配器 POC |
| MiniRAG | 文本块与实体异构图、轻量检索、LiHua-World 长对话评测方法 | 优先借鉴评测集设计；当前不引入 Python RAG 服务 |
| LLM-as-a-Judge bias / CALM | 位置、长度、自我偏好等 Judge 偏差的量化方法 | 纳入 Promptfoo 和故事卡 AI 审阅的评测规范 |
| AutoAgent | 自生成工具、多 Agent 工作流和自修改 | 与单人互动故事核心边界不匹配，不接入 |
| SepLLM | 模型推理期 KV cache 和稀疏注意力优化 | 属于模型服务内部能力；当前 OpenAI-compatible 应用层不接入 |
| OpenGraph / AnyGraph / VideoRAG | 图基础模型或长视频检索 | 当前没有对应产品需求，不进入路线图 |

当前最有价值的不是安装完整框架，而是建立 Storybound 自己的召回基准。查询集至少包含单跳事实、多跳关系、时间顺序、章节总结、分支隔离、秘密权限、用户修正和无答案负例，并保存期望 supporting item。只有当前 lexical / FTS hybrid 无法达到质量要求，且大型外部资料已经进入产品范围时，才比较 MiniRAG、LightRAG 或 OpenViking。

任何外部召回后端都只能接在 `RecallProvider` 类边界之后：SQLite 发送经过范围裁剪的派生文档，外部系统返回候选 ID、分数和轨迹，Storybound 再次校验故事版本、conversation、活动分支、checkpoint 和知识权限。服务不可用时必须回退到本地 lexical，不得阻断核心游玩。

### 3.4 Prompt 文案外置与行为回归

**证据等级**：已核实  
**优先级 / 工作量**：P2 / M

**现状**

核心应用规则位于 `apps/server/src/services/prompt/contextCache.ts` 的 `getStaticContext`；当前 profile 主要描述 block 顺序、预算和快照版本，没有完整承载文案变体。

**建议方案**

- 将不可变的应用约束与可配置的叙事风格分开。应用约束不能被故事类型、用户文案或 Provider 变体覆盖。
- 文案维度优先使用 `locale`、故事类型和模型能力，不直接以 Provider 名称复制整套 Prompt。
- profile 必须包含版本和内容 hash；对话快照继续保存实际使用版本。
- golden snapshot 用于检测结构变化，另用固定场景 eval 检测越权代替玩家决策、输出 JSON 或暴露元评论等行为回归。

**验收标准**

- 缺少或无效 profile 时有稳定默认值。
- 切换语言或风格不会改变必需规则的优先级。
- 旧对话仍能追溯创建和生成时使用的 profile 版本。

### 3.5 Director MOD 的数据访问

**证据等级**：待测量  
**优先级 / 工作量**：P2 / S-M

`pacing-director` 等 MOD 会在 assemble 阶段查询运行数据，但“MOD 越多必然形成性能问题”目前没有查询数和延迟数据支持。

先在不记录正文的前提下测量每次 assemble 的 DB 查询数与 p95 耗时。若同一统计被多个 MOD 重复读取，再向 `collectPromptContributions` 提供只读、per-assemble 的 data loader 或预取上下文。验收要求是查询数和 p95 组装耗时下降，同时没有过度预取、跨会话缓存或 MOD 间可变状态共享。

## 四、后端并发、恢复与可观测性

### 4.1 明确三种并发语义

**证据等级**：已核实  
**优先级 / 工作量**：当前约束文档化 P2 / S，多实例能力 P3 / L

当前实现包含三种不同机制，不能互相替代：

| 目标 | 当前机制 | 能保证什么 | 不能保证什么 |
|------|----------|------------|----------------|
| 会话级互斥 | `generations_active_idx` 和 `assertNoActiveGeneration` | 同一 conversation 只有一个活跃生成 | 跨会话全局容量 |
| 进程级容量 | `GenerationScheduler`，默认 `llmMaxConcurrency = 1` | 单进程内限制并发调用数 | 多实例总并发、任务持久性 |
| 任务恢复 | generation 状态、前端 recovery、启动清理 | 单实例重启后识别未完成任务 | 多实例 owner、心跳和租约 |

当前产品定位是本地单人应用，短期应明确“单服务实例、单数据库写入者”的部署约束，并保留 DB 唯一索引作为会话级最终约束。

只有产品范围明确扩展到多实例后，才设计跨实例容量控制和任务租约。届时至少需要 `ownerId`、heartbeat、lease expiry，以及只回收过期任务的 reconcile。不能让任一新实例启动时直接失败掉其他实例仍在执行的任务。

### 4.2 服务重启后的生成状态已经处理

**证据等级**：已核实  
**优先级 / 工作量**：补测试 P1 / S

`apps/server/src/db/initialize.ts` 的 `initializeDatabase` 已经在启动时将遗留的 `accepted/streaming` 记录更新为 `failed`，错误码为 `SERVER_RESTARTED`。因此不再把“实现启动 reconcile”列为待办。

剩余工作是补充集成测试，验证：

- 重启后遗留任务进入 `failed`，且有 `finished_at` 和稳定错误码。
- 已确认的玩家消息和检查点仍然存在。
- 前端 recovery 能结束轮询、给出可重试提示，并且重试不会产生重复玩家消息。
- 若未来支持多实例，当前无 owner 的全量 reconcile 必须在启用共享数据库前替换。

### 4.3 结构化日志与请求关联

**证据等级**：已核实  
**优先级 / 工作量**：P1 / S-M

`apps/server/src/shared/errors.ts` 对未识别异常仅调用 `console.error`。Provider requestId 已存在，但它不等于应用请求 ID。

建议为每个 HTTP 请求生成或接收经过校验的 `appRequestId`，在错误中间件、generationId 和 Provider requestId 之间建立关联。日志至少包含时间、level、route、status、errorCode、appRequestId、generationId 和耗时。

日志禁止记录 API Key、Authorization、完整 Prompt、完整消息正文和未经筛选的请求体。验收时应能从一次前端错误定位到对应服务请求和生成记录，并有自动化测试验证敏感字段被清除。

## 五、前端体验与稳定性

### 5.1 React 错误边界

**证据等级**：已核实  
**优先级 / 工作量**：P1 / S

当前没有根级 ErrorBoundary 或 TanStack Router 路由级 `errorComponent`。增加根级兜底和会话路由级恢复界面，保留刷新、返回故事库和复制应用请求 ID 的操作。

验收时应注入渲染期异常，确认不会出现空白页面；错误界面不得展示堆栈和敏感内容，路由切换或重试后可以恢复。

### 5.2 流式渲染性能

**证据等级**：待测量  
**优先级 / 工作量**：测量 P1 / S，实施 P2 / M

`useGenerationController` 已用 rAF 合并 delta，但 `streamingText` 更新可能使会话区域重新渲染。仅凭字符串 `current + delta` 不能断言实际瓶颈必然是 O(n²)，内联 handler 数量也不能单独证明需要全面 `useCallback`。

先使用 React Profiler 在短、中、长三种会话和持续流式输出场景记录：

- 每秒 commit 次数和 p95 commit duration。
- 历史消息项的重复渲染次数。
- Markdown 解析耗时、长任务和可见掉帧。
- 诊断轮询对会话主树的影响。

若基线确认问题，再依次考虑隔离流式气泡、将诊断状态移出时间线主树、稳定必要回调、memo 历史消息项，以及降低流式 Markdown 重解析频率。只对 Profiler 证明有效的边界增加 memoization。

验收阈值应基于目标设备和基线数据确定；至少要求历史消息不会随每个流式批次全部重渲染，优化前后有同场景对比记录。

### 5.3 替换 `window.prompt`

**证据等级**：已核实  
**优先级 / 工作量**：P2 / M

`window.prompt` 同时用于 JSON、标题和派生存档名称输入。应按数据类型使用受控表单弹层：JSON 提供多行编辑、schema 校验和字段级错误；标题提供长度和空值校验。

弹层需要保留未提交草稿，并具备确认、取消、Esc、初始焦点、关闭后焦点恢复和提交中状态。不要用一个通用 JSON 输入框替代领域表单。

### 5.4 可访问性

**证据等级**：已核实  
**优先级 / 工作量**：P2 / M

模态需要 focus trap、Esc 关闭、背景 inert 和关闭后的焦点恢复；只在 hover 时出现的操作还必须支持键盘和触摸发现。

流式内容不应把每个 delta 都直接送入 `aria-live`，否则屏幕阅读器会被连续播报打断。建议把“正在生成、生成完成、生成失败”放入独立 status region，正文在完成时播报，或经过较长时间窗口节流。验收应覆盖键盘完整操作、触摸设备和至少一种屏幕阅读器。

### 5.5 UUID 与安全上下文

**证据等级**：已核实  
**优先级 / 工作量**：P2 / S

`crypto.randomUUID()` 不只用于发送和重新生成，也用于故事编辑器的多类实体 ID。文档应先明确受支持的部署环境是否只包含 HTTPS 和 localhost。

若需要支持非安全上下文，统一封装 ID 生成器，使用经过验证的 UUID 库或 `crypto.getRandomValues` 能力检测；不得使用 `Math.random`。验收覆盖会话幂等 ID、编辑器实体 ID、能力和场景创建等所有调用点，并验证冲突不会静默覆盖数据。

## 六、测试与契约

### 6.1 当前覆盖

仓库已经有 Playwright E2E，而不是“没有 E2E 用例”：

- `tests/e2e/core-flow.e2e.ts`：创建存档、检查 MOD、固定记忆和结束章节。
- `tests/e2e/http-boundary.e2e.ts`：请求体上限、畸形 JSON 和错误映射。

共享 schema 和服务层也已经有测试，但覆盖数量或文件行数不能代替风险评估，不再以“60 个端点”“测试文件只有 84 行”作为优先级依据。

### 6.2 高风险缺口

| 测试对象 | 关键场景 | 建议层级 | 优先级 |
|----------|----------|----------|--------|
| `useGenerationController` | accepted、delta、completed、failed、取消和重复事件 | hook/component | P1 |
| 断线恢复 | 刷新、SSE 中断、服务重启、恢复轮询结束 | component + E2E | P1 |
| 乐观锁 | 过期 leaf/checkpoint、重新生成竞态、重复 operationId | service + E2E | P1 |
| 启动 reconcile | 活跃任务失败、消息保留、可安全重试 | integration | P1 |
| SSE 契约 | 服务事件可被共享判别联合解析，未知事件明确拒绝 | contract | P1 |
| 核心实体契约 | API request/response 往返、可选字段和错误对象 | contract | P2 |
| 分支与版本 | 选择候选、派生对话后消息路径和检查点一致 | E2E | P2 |

E2E 中的模型输出应使用可控 fake Provider，避免外部网络、费用和随机文本影响结果。完成标准是关键状态转换和恢复结果可断言，不只是页面元素可见。

### 6.3 AI 判断与 LLM-as-a-Judge 可靠性

**证据等级**：方法风险已由公开研究验证，项目基线待建立  
**优先级 / 工作量**：P1 / S-M

Prompt 质量、故事卡 AI 审阅和候选回复比较可以使用 LLM Judge，但 Judge 结果不是确定性事实。状态 Schema、知识权限、Prompt block 顺序、分支和检查点一致性继续由代码和测试判定，不能被模型评分覆盖。

评测至少采用以下控制：

1. A/B 输出交换顺序后重复评分，检测位置偏好；面向多候选时随机化展示顺序。
2. 隐藏模型名、Provider、Prompt 版本和人工标签，避免品牌、自我偏好和锚定影响。
3. 将内容质量与篇幅、格式遵循分别评分，避免更长文本天然获得高分。
4. 关键场景重复运行并报告均值、方差和失败样本；高风险决策使用多个 Judge，并保留分歧而不是只取多数结果。
5. 保存 rubric 版本、Judge 模型、生成参数、输入场景 ID、原始评分和解释，保证回归可追溯；评测数据不得包含真实私人对话。
6. 故事卡 AI 审阅只产生建议。它不能写入故事事实、记忆、知识簿或运行状态，也不能单独形成发布阻断。

验收时需要构造顺序互换、等义不同长度、模型名伪装和提示注入样例，确认报告能够暴露 Judge 不稳定性。若 Judge 分歧超过评测集约定阈值，该项结果标记为不确定，交由确定性规则或人工复核，而不是自动选出胜者。

## 七、产品机会：作为假设验证

> 本节依据 `docs/PRODUCT.md` 的本地单人定位整理。以下内容不是已经确认的需求，进入排期前需要完成对应验证，并遵守剧透显示、知识权限和本地数据边界。

### 7.1 记忆与召回解释

**假设**：用户看到本轮使用了哪些记忆及其原因后，能更快修正错误记忆，并提高长故事连贯性。  
**优先级**：验证 P1，实施待 3.2 评测结果决定。

最小原型只展示实际注入、因预算省略和未命中的项目，并说明来源、命中词或规则。秘密事实和隐藏 lorebook 必须遵守当前剧透设置与权限，不能因为“召回诊断”直接显示正文。

验证指标包括：用户能否正确判断模型本轮使用了什么、完成一次记忆修正所需时间、错误固定率，以及诊断是否造成剧透。若用户无法理解相关性分数，应优先展示自然语言原因，而不是裸分值。

### 7.2 上下文占用提示

**假设**：展示上下文压力和可操作建议，可以减少超限失败并帮助用户理解章节摘要的价值。  
**优先级**：P2，依赖 3.1。

发送前只能展示“估算输入 / 配置预算 / 预留输出”，生成完成后才展示 Provider 返回的实际 usage。接近上限时可以建议结束章节、检查固定记忆或调整模型配置，但不得暗示所有 Provider 都能提供精确实时数据。

验证重点是用户能否区分估算与实际、提示是否能减少上下文错误，以及它是否给对话顶部增加不必要的持续干扰。

### 7.3 首次进入故事

**假设**：内置示例卡提供“一键开始”，能缩短首次可玩时间，而不会妨碍需要自定义身份的用户。  
**优先级**：验证 P1，实施 P1-P2。

原型使用默认开场、玩家和能力直接创建存档，四步配置保留为“自定义”。通过 5-8 名目标用户的任务测试记录首次进入故事耗时、配置中断点和进入后修改默认设置的比例；没有验证结果前不使用“提高留存”作为确定结论。

首次引导只标记对话、行动、旁白三种输入模式和导演入口，不在页面堆放功能说明。用户完成第一次输入后不再自动出现。

### 7.4 导演指令的可发现性

**假设**：常驻入口和当前作用范围标记可以减少模式误用和遗忘持续指令。  
**优先级**：验证 P1，实施 P2。

原型应展示“下一次 / 本章节 / 本次对话”的有效范围，并允许一键清除。快捷键仅在不与文本编辑、输入法和浏览器快捷键冲突时启用，且必须有可访问名称和等价点击操作。

验证用户能否在无提示情况下找到导演入口、判断当前生效范围，并在需要时关闭指令。

### 7.5 分支和版本来源

**假设**：来源标记、面包屑和结构化状态差异能减少存档增多后的迷失。  
**优先级**：P2。

先用包含多个候选版本和两级派生的原型测试用户能否回答“当前存档来自哪里”“选择这个版本会改变什么”。只有正文对比不足以完成任务时，再增加能力消耗、状态、节点和知识簿差异，避免一次展示过多内部结构。

### 7.6 故事卡体检

**假设**：阻断错误、警告和 AI 建议分级，并可跳转到字段，能缩短作者修正时间。  
**优先级**：P3。

确定性错误与 AI 建议必须视觉和语义分离，AI 建议不能阻止发布。Prompt 预览显示估算 token 和必需块占用，并明确它不是 Provider 的最终计费值。验证指标是定位错误和完成修正的时间，而不是建议数量。

### 7.7 备份与恢复的可信信息

**假设**：显示最近备份时间、状态、位置和恢复点来源，可以提升用户对破坏性操作的理解。  
**优先级**：P3。

文案不得承诺“数据不会丢”。本地备份无法覆盖磁盘损坏、目录被删除或备份本身失败。界面应准确说明最近一次成功备份、失败状态、备份位置、恢复会覆盖什么，以及执行恢复前是否会创建当前快照。

验证用户在清空回收站或恢复快照前，能否正确说出操作影响和可恢复范围。

## 八、统一路线图

| 阶段 | 技术工作 | 产品验证 | 完成门槛 |
|------|----------|----------|----------|
| P0 | 当前无已验证事项 | 无 | 出现可复现的数据丢失、安全或核心阻断问题时单独升级 |
| P1 | Token 校准与一次性降级、错误边界、结构化日志、生成/恢复/契约测试、召回基准、LLM Judge 偏差控制 | 召回解释原型、一键开始测试、导演入口测试 | 有自动化回归、可观测数据或完成的用户任务记录 |
| P2 | 按评测选择 FTS5/hybrid 召回实现、流式渲染优化、Prompt profile、MOD 数据访问、表单化、a11y、UUID 封装 | 上下文提示、分支和版本来源 | 达到各节验收条件，且依赖能力已经完成 |
| P3 | 多实例架构仅在部署范围变化后启动 | 故事卡体检、备份与恢复信息 | 有明确范围触发条件或用户验证结果 |

推荐实施顺序：

1. 先补结构化日志、生成恢复测试和测量工具。
2. 用数据完成 Token、召回和流式渲染基线。
3. 优先处理已经证明影响核心流程的问题。
4. 产品原型通过任务测试后，再进入完整实现。
5. 每项完成后回写实际结果、残余风险和优先级变化。
