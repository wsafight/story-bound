# Storybound（入戏）- 产品文档

相关开源产品、可学习设计与实现边界见 [PRODUCT_RESEARCH.md](PRODUCT_RESEARCH.md)。

## 一、产品定位

Storybound，中文名“入戏”，是一款面向个人使用的 AI 互动故事应用。名称既表达“被故事吸引、走进故事”，也呼应装订成册、可以反复翻阅的故事与存档。

用户从故事库选择一张故事卡，阅读背景与人物设定，创建一次独立对话，配置本次故事使用的玩家身份、开场和能力，然后通过对话、行动和旁白持续推进故事。

模型可以连接本地或远程 OpenAI-compatible 服务，由用户选择并按对话保存配置快照。故事卡、对话、记忆、模型配置引用和进度始终以本机 SQLite 为真实数据源，不要求云端账号或同步。

### 产品目标

- 一张故事卡承载一个完整、可重复游玩的故事设定，而不只是一个聊天角色。
- 同一张故事卡可以创建多次对话，每次对话拥有独立的玩家设定、能力、进度和历史。
- 长对话中尽量保持人物、世界规则和关键事实一致。
- 让用户可以查看、修改和修正 AI 使用的故事状态与记忆。
- 通过导演指令控制节奏和创作方向，同时不污染玩家发言与故事事实。
- 通过故事节点、秘密揭示和章节总结让剧情持续推进，而不是退化为无限闲聊。
- 优先服务单人本地使用，不引入账号、社区、评分、付费和多人协作系统。

## 二、核心概念

| 概念 | 定义 |
|------|------|
| 故事卡 | 可重复使用的故事模板，包含背景、人物、玩家模板、能力、开场和故事规则 |
| 人物 | 故事中的 AI 角色，可以有一名主角和多名关联人物 |
| 玩家档案 | 用户可重复使用的个人设定，例如姓名、年龄、外貌和自定义属性 |
| 玩家模板 | 故事卡建议的玩家身份、关系、目标和可编辑范围 |
| 能力 | 本次故事可启用和配置的技能或机制，包括玩家技能、人物技能和故事机制 |
| 对话 | 基于某张故事卡创建的一次独立故事存档 |
| 故事状态 | 当前阶段、场景、时间、关系、物品和其他自定义变量 |
| 记忆 | 用于上下文压缩和召回的用户提醒、历史片段与阶段摘要，不作为事实真相来源 |
| 故事节点 | 带有前置条件、揭示内容、状态变化和完成条件的可选剧情事件 |
| 事实与秘密 | 对世界事实、线索、传闻以及各人物知情范围的结构化记录 |
| 导演指令 | 不属于故事正文的临时或持续创作要求，例如调整节奏、氛围和人物出场 |
| 章节 | 对连续一段故事的范围、摘要、状态和关键变化的存档单元 |
| MOD | 由受信任扩展目录提供、可按存档启用的故事生成规则；配置随运行时检查点保存 |

最重要的数据关系是：

```text
一张故事卡
  ├── 多个人物
  ├── 一个玩家模板
  ├── 多项可选能力
  ├── 多个开场场景
  ├── 多个故事节点
  ├── 初始事实与秘密
  └── 多次独立对话
        ├── 本次设定快照
        ├── 故事状态
        ├── 运行时检查点
        ├── 节点进度
        ├── 事实、秘密与记忆
        ├── 章节
        ├── 导演指令
        ├── 当前 MOD 配置与变更事件
        ├── 待确认的故事变化建议
        └── 消息历史
```

故事卡是模板，对话是存档。修改故事卡不能静默改变已经开始的对话。

## 三、核心用户流程

```text
进入故事库
  → 选择故事卡
  → 查看故事详情和已有对话
  → 新建对话
  → 选择开场
  → 配置玩家设定
  → 选择和配置能力
  → 确认本次故事设定
  → 开展故事
  → 使用行动、能力或导演指令推进故事
  → 结束章节并保存摘要
  → 自动保存、继续、派生新对话或结束
```

### 再次进入故事卡时

用户可以：

- 继续最近一次对话。
- 从已有对话列表选择一个存档。
- 使用上一次配置快速新建对话。
- 从头配置新的对话。

## 四、主要页面

### 1. 故事库

首页展示所有故事卡，而不是单独的角色卡。

每张卡片显示：

- 封面图。
- 故事标题。
- 一句话故事钩子。
- 主角名称或主要人物。
- 类型标签。
- 已有对话数量。
- 最近游玩时间和进度摘要（如有）。

支持的操作：

- 点击卡片进入故事详情。
- 继续最近对话。
- 新建、编辑、复制、归档故事卡，或将已归档故事卡移入回收站。
- 按标题和标签搜索；故事卡数量较少时不需要复杂筛选器。

卡片只负责帮助用户选择故事，不在卡片表面展示完整背景和人物长文。

故事库另设“独立存档”列表，用于显示来源故事卡已被物理删除、但仍可依靠自身快照继续游玩的对话。独立存档显示对话名称、原故事标题、最近游玩时间和进度摘要，可以继续、归档或移入回收站，但不能再编辑或恢复来源故事卡。

### 2. 故事卡详情

详情页是开始故事前的主要阅读和管理页面，包含：

- 故事简介与完整背景。
- 世界规则、面向用户的内容提示与模型必须遵守的内容边界。
- 主要人物和人物关系。
- 推荐玩家身份。
- 可用能力与故事机制。
- 可选开场场景。
- 故事节点数量和无剧透的推进说明。
- 事实与秘密数量；具体秘密默认折叠，主动进入剧透模式后才显示。
- 已有对话列表。

主要操作：

- `新建对话`。
- `继续最近对话`。
- 打开指定对话。
- 编辑或复制故事卡。
- 运行故事卡体检。

### 3. 新建对话

新建对话采用简短的分步配置流程。

#### 第一步：选择开场

- 选择故事卡提供的开场场景。
- 预览初始地点、时间、在场人物和开场文本。
- 故事卡可以设置一个默认开场。

#### 第二步：配置玩家

- 从已保存的玩家档案中选择，或临时创建一个玩家。
- 载入故事卡提供的推荐玩家模板。
- 修改本次故事允许编辑的字段。
- 明确玩家与主要人物的初始关系和目标。

玩家档案提供通用个人信息，玩家模板提供故事需要的身份。两者合并后的结果只保存到本次对话快照中。

一张故事卡只有一份玩家模板。当不同开场需要不同的介入身份时，由开场覆盖模板中允许编辑的字段——例如同一个故事既可以“作为记者介入”也可以“作为当事人亲属介入”。锁定字段不受开场覆盖影响。

#### 第三步：选择和配置能力

- 按类别展示故事卡允许使用的能力。
- 选择本次启用的能力。
- 配置等级、强度、次数、消耗、冷却或其他参数。
- 支持恢复故事卡默认值和载入上一次配置。
- 对互斥、缺少前置条件或超过数量限制的配置给出明确提示。

#### 第四步：确认并创建

确认以下内容：

- 对话名称。
- 开场场景。
- 玩家身份。
- 已启用能力及参数。
- 主要人物和初始关系。
- 可选的模型参数预设。

创建时保存故事卡版本和完整配置快照，然后进入故事界面。

### 4. 故事对话

#### 顶部区域

- 返回故事详情。
- 显示故事标题、对话名称和当前场景。
- 显示保存状态和模型运行状态。
- 打开故事状态与设定面板。

#### 消息区域

- 区分玩家消息、人物消息、旁白和时间线事件。
- 多人物场景中显示具体发言人物。
- 模型回复采用流式显示。
- 场景切换、阶段变化、能力使用等以独立的时间线事件显示；事件与消息按时间合并展示，但不参与消息分支的父子关系。

每条消息可执行：

- 复制。
- 重新生成。
- 编辑玩家消息后重试。
- 从该处派生独立对话。
- 并排比较同一轮的多个生成版本，再选择当前采用版本。
- 标记为重要记忆。

重新生成不会直接覆盖原内容；系统保留当前选中的版本，避免误操作丢失故事。

同一轮的多个生成版本不仅包含不同的故事正文，也可能对应不同的能力消耗、故事状态、节点进度和知识簿。系统必须为每个可采用版本保存运行时检查点。用户选择另一个版本时，消息路径和结构化故事状态在同一事务中切换，不能只替换显示文本。

同一对话只允许在最后一轮尚未继续推进时直接切换生成版本。已经沿某个版本继续产生新消息后，选择旧版本或编辑历史玩家消息都会改为“从此处派生新对话”，避免静默丢弃后续剧情。

重新生成和编辑重试只对当前进行中章节的最后一轮开放。其他历史消息只提供复制、查看、标记记忆和“从此处派生新对话”；派生结果带有原有设定、目标消息之前的剧情及对应运行时状态，是完全独立的存档。

#### 输入区域

输入支持三种模式：

| 模式 | 用途 | 示例 |
|------|------|------|
| 对话 | 玩家直接说出的话 | `我会和你一起去。` |
| 行动 | 玩家执行的动作 | `检查桌上的旧信件。` |
| 旁白 | 补充场景、时间跳转或创作方向 | `三天后，暴雨仍未停止。` |

支持多行输入、停止生成和失败后重试。模型生成期间不丢失尚未发送的草稿。

#### 导演面板

导演面板与玩家输入严格分离，用于控制下一轮或后续一段故事的创作方向：

- 调整节奏：放慢、正常或加快。
- 调整氛围与叙事重点。
- 请求某个人物登场或暂时退场。
- 建议推进、暂停、跳过某个可用故事节点。
- 发起合理的时间跳转或场景转换。
- 输入一条自由导演指令。

每条导演指令需要选择作用范围：仅下一次回复、本章节或本次对话。默认使用“仅下一次回复”。导演指令单独保存，不显示为玩家消息，不自动进入记忆，也不能覆盖世界硬规则、已确认事实和受保护状态。

#### 故事 MOD

- 设置页负责加载可信 MOD 和维护默认配置；加载 MOD 不会自动改变已有存档。
- 对话页可以在故事进行中启用、停用或调整提示词型 MOD。
- 每次变更必须绑定当前消息叶与运行时检查点，并创建新的检查点和可见时间线事件，只影响之后的生成。
- 生成进行中禁止修改 MOD。需要迁移结构化状态或改变规则语义的 MOD 只能从新章节或新存档开始生效。
- 对话保存 MOD 版本与配置快照；重新生成、重试和分支必须使用对应检查点的快照。
- 动态加载仅面向受信任内置代码。用户自定义扩展优先采用声明式提示词配置，不把任意服务端代码当作安全沙箱执行。

#### 能力快捷栏

- 只显示当前可用且由玩家主动使用的能力。
- 显示次数、消耗、冷却和不可用原因。
- 点击能力后填写目标或必要参数，再确认执行。
- 确定性状态先由应用提交，模型随后叙述结果。
- 模型不支持工具调用时仍可通过快捷栏使用能力。

#### 故事状态面板

面板集中显示：

- 本次玩家设定。
- 已启用能力、当前次数和冷却。
- 当前阶段、地点和时间。
- 人物关系列表和关系图视图。
- 物品、任务和自定义状态。
- 当前故事节点及其他可用节点。
- 章节摘要与固定记忆。
- 事实、线索、秘密和各人物知情范围。

用户可以在故事进行中调整允许修改的能力和状态。所有修改形成可见的时间线事件，只影响修改后的消息，避免上下文在无提示的情况下变化。

状态面板提供变更历史，可以撤销最近一次结构化状态修改。撤销以一条新的修正事件呈现，不删除历史记录，也不改动已经生成的故事正文。

知识簿默认只显示玩家当前已知内容。查看隐藏秘密必须主动开启剧透模式，关闭后恢复无剧透视图；该开关只保护游玩体验，不作为安全权限。

#### 章节与回顾

- 创建对话时自动建立第一章。
- 用户可以在场景切换或关键节点完成后结束当前章节。
- 结束章节时生成可编辑的标题和摘要，并提取事实、关系、节点和未完成事件的变化建议。
- 摘要可以编辑和锁定；状态与事实建议必须经过校验或用户确认。
- 结束后自动开始下一章，旧章节原文仍可查看。
- 完成整个故事后可以导出为 Markdown 故事、剧本或带章节摘要的存档。

### 5. 故事卡编辑

故事卡支持结构化编辑：

- 基础信息。
- 世界背景与规则。
- 人物列表与人物关系。
- 玩家模板。
- 能力列表与参数。
- 开场场景。
- 故事节点及其前置、完成和揭示条件。
- 初始事实、秘密和人物知情范围。
- 故事阶段和自定义状态字段。
- 模型提示规则与默认生成参数。

支持预览最终发送给模型的故事设定。保存修改时增加故事卡版本；已有对话继续使用创建时的旧版本快照。

故事卡体检优先执行确定性检查，包括缺失必填字段、无开场、节点或人物引用不存在、节点条件不可达、能力无处理方式、状态路径无效和提示词预算过高。确定性错误允许保存草稿，但禁止用该版本新建对话。人物动机矛盾、节奏空洞和秘密可能提前泄漏等语义问题交给可选 AI 审阅；AI 只能给出建议，不能自动修改故事卡或改变错误级别。

## 五、故事卡内容结构

### 1. 基础信息

| 字段 | 说明 |
|------|------|
| 标题 | 故事卡名称 |
| 封面 | 故事库使用的图片 |
| 简介 | 一句话故事钩子 |
| 描述 | 详情页使用的故事介绍 |
| 标签 | 类型、氛围和主题标签 |
| 内容提示 | 告知用户故事可能包含的敏感主题，不表示模型应避开这些主题 |
| 内容边界 | 用户明确不希望生成的内容及处理方式，用于约束模型 |
| 版本 | 追踪故事卡修改，保护旧对话 |

### 2. 背景与世界规则

- 故事发生的时代、地点和前置事件。
- 世界中的客观规则和限制。
- 模型必须遵守的叙事视角、风格和内容边界。
- 只有部分人物知道的信息不应写入公共背景，而应放入事实与秘密列表并配置 `known_by`。

### 3. 人物设定

每个人物包含：

- 名称、头像和身份。
- 外貌与行为特征。
- 性格与价值观。
- 说话方式和常用表达。
- 当前目标与长期动机。
- 人物的一般知识范围与认知限制；具体事实和秘密统一在知识簿中配置。
- 与玩家及其他人物的关系。
- 是否是主要人物、是否允许主动发言。

人物可以复用于卡片编辑，但实际对话使用故事卡中的人物快照，保证上下文稳定。

### 4. 玩家设定

玩家档案保存可跨故事复用的信息：

- 姓名。
- 年龄。
- 外貌。
- 通用背景。
- 自定义属性。

故事卡的玩家模板保存与当前故事有关的信息：

- 推荐身份。
- 与人物的初始关系。
- 进入故事的原因。
- 初始目标。
- 默认属性。
- 必填字段、可编辑字段和锁定字段。

不为某类故事固定增加专用数据库字段。特殊属性统一使用故事卡定义的自定义字段，以便不同故事自由扩展。

### 5. 能力

能力分为：

- 玩家技能：由玩家主动使用的故事内能力。
- 人物技能：限定人物可以使用的能力。
- 故事机制：例如判定、关系推进、物品或状态追踪。

每项能力至少包含：

| 字段 | 说明 |
|------|------|
| 名称 | 向用户和模型显示的名称 |
| 类别与归属 | 玩家、人物或故事机制 |
| 描述 | 能力在故事中的含义 |
| 使用规则 | 前置条件、效果和限制 |
| 配置定义 | 可配置参数的类型、范围和选项 |
| 默认配置 | 新建对话时使用的值 |
| 提示词规则 | 启用后如何影响模型行为 |

第一版以“结构化配置 + 提示词约束”为主。需要准确计算的次数、冷却和数值由应用维护，模型只负责叙述，不允许模型自行修改受保护状态。

### 6. 开场场景

每个开场包含：

- 标题和简短说明。
- 初始地点、时间和在场人物。
- 玩家进入场景的方式。
- 开场旁白或人物的第一条消息；人物发言需要指定对应人物。
- 初始故事状态覆盖值。

开场文本既是用户看到的第一条内容，也是本次对话快照的一部分。

### 7. 故事节点

故事节点提供可选的剧情推进结构，不要求故事按固定线性流程运行。每个节点包含：

- 标题和无剧透简介。
- 前置状态、前置事实和前置节点。
- 建议场景、参与人物和叙事目标。
- 可以揭示的事实、线索或秘密。
- 完成条件及完成后的状态变化。
- 优先级、是否可跳过以及剧透级别。

对话中的节点状态为 `locked`、`available`、`active`、`completed` 或 `skipped`。应用根据经过校验的状态和事实计算可用节点；模型只能建议激活或完成节点，不能绕过条件直接改变节点状态。用户始终可以在导演面板中确认、跳过或手动修正。

### 8. 事实、线索与秘密

每条知识记录包含：

- 内容类型：客观事实、人物认知、传闻或线索。
- 真伪状态：确定、存疑或错误。
- 内容和来源。
- 当前知情者：玩家、指定人物或所有人。
- 是否属于秘密。
- 揭示条件和关联故事节点。
- 生命周期：有效或已失效；是否已向玩家揭示由知情者列表推导。
- 是否锁定，锁定内容不能被自动摘要覆盖。

“客观事实”和“人物相信的事情”必须分开。人物可以相信错误信息，但应用不能因此修改世界事实。故事卡中的初始记录在创建对话时复制为运行时知识快照，之后每次对话独立变化。

### 9. 故事阶段与状态

不再把所有故事固定为四个“沉沦阶段”。故事卡可以自定义阶段名称和数量，例如初遇、试探、合作、冲突和结局。

除阶段外，还可以维护：

- 地点与时间。
- 人物关系。
- 任务和关键事件。
- 物品与资源。
- 故事卡自定义变量。

状态变化可以来自用户手动调整、能力规则或经过校验的模型建议。模型输出不能未经校验直接覆盖应用状态。

故事卡需要同时定义默认状态、状态结构和字段策略。状态结构只描述数据类型与取值范围；字段策略单独描述哪些路径允许用户在创建时或故事进行中修改，哪些路径只能由应用规则维护。阶段、当前地点、时间和在场人物使用应用保留的标准路径，自定义变量放在故事卡自己的命名空间中。

## 六、上下文与记忆

每次发送消息时，模型上下文按以下顺序组装：

1. 应用级行为规则。
2. 故事卡快照中的背景与世界规则。
3. 按当前叙述角色权限过滤后的相关事实与知识。
4. 当前在场人物设定及各自允许知道的信息。
5. 本次玩家设定。
6. 已启用能力及有效参数。
7. 当前章节、场景、故事节点与故事状态。
8. 固定记忆、相关历史摘要和较早章节摘要。
9. 最近对话历史。
10. 当前有效的导演指令。
11. 用户本次输入及输入模式。

导演指令的优先级低于应用规则、世界硬规则和已确认事实。导演指令只影响创作方式，不能自动成为故事事实；只有实际发生并经确认的内容才能进入状态、知识簿或记忆。

长对话不能只依赖“最近 N 条消息”。系统应维护：

- 最近消息：保持当前对话节奏。
- 阶段摘要：压缩较早发生的情节。
- 章节摘要：在跨章节时保留主要进展和未完成事件。
- 固定记忆：保存用户希望每轮考虑的重要提醒，但不替代知识簿中的事实。
- 知识簿：记录事实、秘密状态以及各人物的知情范围。
- 用户修正：允许删除、编辑或锁定错误记忆。

## 七、对话生命周期

| 状态 | 说明 |
|------|------|
| 进行中 | 可以继续发送消息 |
| 已完成 | 故事已结束，默认只读但可以恢复 |
| 已归档 | 从常用列表隐藏，数据仍保留 |
| 回收站 | 已执行删除操作，可以在清空回收站前恢复 |

对话允许“进行中与已完成”互相转换；进行中或已完成的对话可以归档，归档后可以恢复到归档前状态；任何非回收站状态都可以在二次确认后移入回收站，并在清空前恢复到删除前状态。

回收站提供独立入口，显示进入时间、来源和占用空间。清空回收站是唯一会物理删除数据的操作，执行前自动创建一次备份并要求二次确认。

每次对话自动保存：

- 故事卡版本与完整快照。
- 玩家和能力配置快照。
- 当前故事状态。
- 消息版本、运行时检查点与派生来源。
- 节点进度、知识簿和导演指令。
- 待确认或已处理的故事变化建议。
- 章节、摘要和固定记忆。
- 最近游玩时间。

归档故事卡不影响已有对话。只有已归档的故事卡可以移入回收站；清空回收站后删除故事卡模板，其已有对话保留为“独立存档”，继续使用创建时快照。删除对话需要二次确认，并明确它在清空回收站前可以恢复。

## 八、数据边界

本文档只定义概念、关系和产品规则，不定义字段名、类型和数据库结构。字段级定义只有一处出处：`TECH.md` 第六节数据库设计。两边都写会随修改逐渐分歧。

产品层面需要保证的数据边界：

- 故事卡及其子项（人物、玩家模板、能力、开场、故事节点、初始事实）构成模板；对话及其子项（消息、状态、节点进度、知识簿、章节、导演指令、记忆、变化建议）构成存档。
- 对话创建时把模板完整复制为快照。此后修改故事卡不影响任何已存在的对话。
- 每个能够成为当前版本的消息节点关联一份运行时检查点，至少覆盖故事状态、能力运行状态、节点进度和知识簿。重新生成、选择版本和派生对话都从目标消息对应的检查点恢复，不能沿用另一条路径的当前状态。
- 玩家档案跨故事复用，但一旦参与创建对话就只以快照形式存在，删除档案不影响已有存档。
- 事实与人物认知分开记录，知识簿是知情范围的唯一出处，记忆不是。
- 应用维护的受保护状态（次数、冷却、关系值、物品数量）不接受模型文本直接写入。
- 重新生成、编辑重试和版本切换只作用于当前进行中章节的最后一轮。其他历史改写统一派生新对话，并从目标消息的运行时检查点初始化。

## 九、设置

- 玩家档案管理。
- 本地或远程模型 Provider 管理；密钥只保存在服务端凭据存储中，不随普通 API、故事导出或对话快照返回。
- 默认模型、上下文窗口、最大输出和生成参数。
- 思考模式可关闭、自动或启用；支持的 Provider 可以进一步设置思考强度。思考内容不进入故事正文。
- 上下文长度和最近消息预算。
- 自动摘要频率。
- 默认导演指令范围与剧透显示方式。
- 主题设置。
- 数据库备份与恢复。
- 故事卡和对话的 JSON 导入导出。

## 十、实施优先级

### 第一阶段：先把故事跑起来

目标是用一条可玩的纵向流程尽快验证模型对话手感。基础故事卡编辑器与模型 Provider 配置纳入当前开发基线；动态状态、节点、知识簿和任意历史分支仍按后续阶段推进。

- 内置至少 2 张只读示例故事卡，随首次启动写入；每张提供一个默认开场和一套可直接使用的玩家配置。
- 故事库与故事卡详情。
- 简化的新建对话配置：玩家基本信息、提示词型能力开关和确认。
- 每张故事卡支持多个独立对话。
- 玩家、能力和故事卡快照。
- 自动创建第一章，但第一阶段不开放章节管理和手动状态编辑。
- 基础聊天、流式回复与自动保存。
- 停止、失败重试、重新生成最后一条回复，以及编辑最后一条玩家消息后重试。
- 模型离线提示、进程重启恢复和用户主动创建的本地安全备份。
- 本地或远程 OpenAI-compatible Provider 配置、连通性检查、模型选择和可选思考模式。
- 新建、编辑、校验和发布基础故事卡；内置故事卡保持只读，但可以复制为用户草稿。

### 第二阶段：让故事持续推进

- 在基础编辑器上补齐更复杂的结构化编辑：动态状态、节点、知识簿与版本比较。
- 动态玩家字段、默认故事状态和字段策略编辑。
- 故事节点、条件、进度和揭示内容。
- 事实、秘密与人物知情范围。
- 确定性故事卡体检与故事变化建议。
- 故事状态面板与状态撤销。
- 导演面板和能力快捷栏。
- 章节结束、摘要和回顾。
- 固定记忆、相关检索与上下文预览。
- 能力次数、冷却和规则校验。
- 多人物发言与人物知识边界。
- 故事卡可选 AI 审阅。

### 第三阶段：提高可控性

- 并排比较同一轮的多个版本，以及从任意历史消息派生新对话。
- 故事卡版本比较。
- JSON 导入导出，以及用户可见的数据库备份与恢复工具。
- 更复杂的自动状态提取与规则系统。
- 可复用世界书与人物原型库；创建对话时仍必须生成独立快照。

### 阶段验收原则

- 第一阶段必须能在首次启动后不编辑故事卡直接开始游玩；模型离线、生成失败、取消和服务重启都不能丢失已经确认的玩家消息。
- 同一故事卡创建两次对话后，消息、玩家配置和运行状态必须完全隔离；修改模板不能改变旧对话快照。
- 第二阶段的任何结构化变化都必须可见、可校验并关联运行时检查点；模型文本不能绕过确认流程修改受保护状态或知识簿。
- 第三阶段选择版本或派生对话后，消息路径与结构化状态必须一致；导入、恢复和物理删除都必须先通过完整性检查并保留可恢复备份。
- 每个阶段都以对应的端到端流程、确定性集成测试和固定 Promptfoo 数据集作为完成条件，不能只以页面或表结构已经存在作为完成标准。

不在当前范围内：账号系统、云端同步、故事市场、公开分享、评论评分、付费和多人实时协作。
